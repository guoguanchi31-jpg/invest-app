# 行级提交确认、历史基线与审计载荷契约

日期：2026-10-01。状态：已实现。补充
[2026-09-30 财务边界决策](2026-09-30-financial-boundaries.md)。

## 问题

已提交动作在刷新失败后滞留，后续手动读取不能释放；余额相等、建账日期和调整记录
被误当作历史完整的证据；恢复只按通用字段名递归，嵌套实体主键缺少准确归属。
并发测试排除了合法的执行顺序，固定月份测试又依赖实际日期。

## 决策

1. 行级提交和资源共享单调事件序号。提交终态与成功读取分别记录序号；
   只有当前身份、对应资源且开始晚于终态的读取，才能释放已提交/失效意图。
   月份是相关资源键的一部分。写入进行中和结果未知时不释放原操作键。
   不依赖全局“全部刷新成功”，不使用可能回拨的设备时间。
2. 新账户显式声明零基线或期初流水基线，后者必须有唯一有效且日期匹配的流水。
   `matches` 与 `history.status` 独立；投资账户的基线只描述 `cash_available`。
   schema 9 对既有账户默认 `unknown`，不推断、不增减资金。JSON v8 保留元数据，
   v1–v7 缺失字段按未知处理；无证据的显式完整基线在恢复预校验阶段拒绝。
3. 审计新写入 `payload_version=1`；领域层声明目标、分配、目标记录、预算及
   投资交易前后快照的结构。基础设施提供新 ID 映射，领域规则不访问数据库。
   v0 已知结构按相同规则映射；未知结构/版本保留为明确的历史命名空间。
   已删除实体使用稳定的 `legacy:` ID，重复恢复不重复加前缀。
4. 现金并发测试校验允许的序列化结果及事实守恒。指定任一命令先获真实家庭锁，
   再让其余写入竞争；保持业务锁协议不变。核对先行时允许三成功且现金 400，
   其余先行时核对 409、两成功且现金 500。随后重放成功命令核对幂等性。
5. 固定月份测试局部固定业务时钟，不固定身份认证和超时时钟；跨月创建与查询
   使用独立边界用例，避免随运行日期切换而误报。

## 兼容与代价

- 不修改历史迁移，只追加 schema 9；JSON 备份版本升至 8，兼容读入 1–7。
- 旧账户可能余额完全一致但仍报告历史来源未知。这是证据不足的准确表达；
  本次没有引入批量补期初或自动资金修复。
- 未知审计载荷保留原文与版本，无法作为当前实体链接使用。
- PostgreSQL 和容器恢复演练继续由专用环境执行；SQLite 通过不能替代它们。

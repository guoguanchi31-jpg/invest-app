# 财务提交、读取、日历与家庭恢复边界

日期：2026-09-30。状态：已采纳并实现。关联：
[架构审查 R1–R7](../architecture-review-2026-09-30.md)、
[执行验收](../architecture-remediation-2026-09-30.md)。

## 背景

现有模块化单体与事务模型适合家庭财务应用。已发现的问题集中在边界：
提交成功后读取失败会复活表单；组合查询可能混合两个时刻；默认日期采用 UTC；
恢复依赖全表锁和原始 ID；公共表单层仍承担业务分派。

## 决策

1. **提交确认独立于资源刷新。** `useSubmission` 确认写入后结束本次表单意图，
   读取失败只允许重新加载。操作键属于业务意图，未知结果保留原键，已确认、
   过期和失效均有明确终态。服务端返回机器错误码，客户端不解析中文提示来换键。
2. **响应拥有读取事务。** 根查询拥有 `consistent_read_connection`，子查询显式
   接受连接。PostgreSQL 使用 `REPEATABLE READ READ ONLY`，SQLite 使用 `BEGIN`。
   当天仓库展示点可在响应中计算，GET 不负责持久化。
3. **业务日历统一。** `BUSINESS_TIMEZONE` 默认 `Asia/Shanghai`；会话传给前端。
   日历日期与事件时间戳分别处理，历史日期不自动改写。
4. **领域规则与 SQL 分离。** `domain/accounting.py` 计算净余额变化及核对规则，
   `infrastructure/accounting_store.py` 持有具体 SQL。保留函数式 `conn/context`，
   不引入通用 Repository 或依赖注入容器。
5. **在线写入按家庭协调。** 锁顺序为家庭事务锁、命令键、账户 ID 升序、子记录。
   同家庭写入串行；不同家庭使用不同 PostgreSQL advisory lock，读取仍采用 MVCC。
   快照按家庭提交，后台行情和命令清理遵守同一顺序。
6. **恢复先准备、再原子替换。** 锁外读取和持久化恢复前副本；锁内重查指纹。
   数据库生成新 ID，显式映射外键、审计和转账引用，保留账单导入去重命名空间。
   不重置全局序列。恢复请求纳入幂等协议，旧键失效，本次恢复键仍可重放。
7. **业务装配位于 app/feature。** 每个 feature 拥有草稿、字段和动作，
   `app/actionDefinitions` 与工作区负责分派；shared 只提供通用生命周期和组件。

## 取舍与约束

- 家庭锁降低单家庭写并发，换取恢复、分类、成员、资金和后台写入的确定顺序。
  当前规模可接受；未来有明确吞吐证据时再评估更细协议。
- 一致性读取事务内禁止等待网络；长查询和大导出应持续观察执行时间。
- 恢复后的记录 ID 会变化，调用方需丢弃旧草稿、筛选、明细和缓存。导入去重
  使用稳定命名空间，审计内不存在的历史实体标为 `legacy:`，避免误关联。
- JSON v7 和 schema v8 是新增兼容层；旧 JSON v1–v6 仍接受。恢复副本可在失败或
  竞争后保留，文件存在不表示数据库恢复已提交。
- 离线迁移和整库 PostgreSQL 运维恢复采用停机流程，独立于在线家庭协议。
- 运维备份用原子文件、校验和、失败状态与隔离恢复演练；异机加密存储和告警接收
  仍由部署环境提供，不在应用内新增云厂商依赖。

## 验证

资金与审计回滚、读写交错、日期边界、旧键重放、恢复 ID 映射和跨家庭隔离都有
回归入口。CI 分开运行 PostgreSQL、前端、真实浏览器及备份演练。
本机实际执行结果及外部环境缺口以执行验收文档为准，不能把 CI 配置视为运行证明。
